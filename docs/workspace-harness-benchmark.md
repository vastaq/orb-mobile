# 工作区编辑工具的对照评测

## 为什么改搜索和读取

SWE-agent 将文件搜索和有行号的局部查看器连起来，并在同一模型上比较了搜索方式、查看窗口与编辑反馈。Aider 的编辑器要求模型给出对应原文，在失败时返回可用于重新定位的上下文；它的编码基准通过运行代码评分。Orb 借鉴了从搜索定位到局部编辑的流程，并保留已有工作区的整文件版本校验。[SWE-agent 论文，特别是表 3](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf) · [Aider 编辑器](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/editblock_coder.py#L78-L124) · [Aider 评测方法](https://aider.chat/docs/benchmarks.html)

| 操作 | 基线 c8683b5 | 候选版 |
| --- | --- | --- |
| 搜索长行 | 返回匹配行的前 200 个码点，关键词可能落在可见范围外 | 返回关键词附近最多 200 个码点的原文，以及每个命中文件的版本哈希。可通过 `context_lines` 同时取上下各 1 至 3 行原文 |
| 查看命中位置 | 搜索给行号；读取接受从文件开头算起的字符偏移 | 可传 1 起始的 `start_line` 和 `line_count`。默认取 40 行，单次最多 8,000 个码点，支持从 `next_offset` 继续 |
| 局部编辑 | 原文不存在和原文重复时得到同一个错误 | 告知不存在或重复，重复时给出前几个位置的行号。局部编辑仍要求唯一精确匹配和正确版本；整文件覆盖仍引导先读全文 |
| 同文件多处修订 | 每次只能改一处，后一次依赖前一次写入返回的新哈希 | 一次提交最多 8 组独立替换，使用同一份原文和版本。出现不匹配、重叠或过期版本时，SQLite 事务不写入任何一处 |

## 任务与评分

三道配送报价题由同一个生成器构造。验收借鉴 SWE-bench 对修复行为和原有行为分别打分的方法。每次都从相同的工作区、空白聊天和一条中文需求开始。用户要求改指定站点的费率，保留其他记录及排版，运行程序，把两行报价保存为文件。短文件题用于检查常见任务是否退步，两个长文件题用于检验跨页定位和同名记录消歧。[SWE-bench 官方评分代码](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py)

| 任务 | C 源码大小 | 要改的业务记录 |
| --- | ---: | --- |
| 长文件单处 | 20,992 B | 只改目标站点工作日的起步费，节假日费率保持原值 |
| 长文件双处 | 20,992 B | 分别改工作日起步费和节假日每公斤单价 |
| 短文件对照 | 1,490 B | 与单处题相同的操作，每张表只有 4 站 |

必须同时满足六项条件：对话正常完成、聊天有实际运行成功的回执、结果文件正确、修改区域外的 C 原文逐字保留、项目说明完好、保存的程序通过四行隐藏输入。隐藏输入覆盖目标站点的新重量和相邻站点，独立于模型答案。修改区域内部允许等价写法。判分器不要求固定工具顺序。原始程序和等价参考修复在随包 xcc 上分别运行公开及隐藏样例，三题共 12 次执行，均符合预期。

另外保留一道编写交班卡的文档题，产品改动冻结后才运行。27 节虚构巡展手册共 10,966 字节。用户要求更新其中一节的两个编号，并把一个新编号和一个需要从手册查到的原有编号写进两行交班卡。评分检查目标值、其他原文的完整性及交班卡，目标行允许等价 Markdown 格式。它通过同一个聊天控制器、模型协议和 SQLite 工具运行，覆盖纯文本工作区场景。


## 真实 API 结果

基线为 `c8683b5`，最终产品代码为 `7ab2065`。Android 16 专用模拟器经同一开发机转发器使用 DeepSeek Chat Completions 和 OpenAI Responses。每个模型、每个版本、每道题独立开一轮新对话；保持最多 6 轮工具交互、16 次调用的生产上限。一次模型响应可触发多个工具，最后一条拒绝继续执行的响应也计入模型轮数。表中为基线 → 最终版。输入数来自供应商的完整响应，包含已缓存输入；这些数字不能直接换算成账单。

| 模型 | 任务 | 整体结果 | 模型轮数 | 工具调用数 | 输入 token | 输出 token |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| deepseek-flash | 长文件单处 | 通过 → 未通过 | 6 → 7 | 7 → 8 | 54,967 → 55,776 | 699 → 784 |
| deepseek-flash | 长文件双处 | 未通过 → 通过 | 7 → 5 | 7 → 6 | 57,238 → 29,763 | 700 → 731 |
| deepseek-flash | 短文件 | 通过 → 通过 | 5 → 5 | 5 → 5 | 13,448 → 15,228 | 595 → 582 |
| gpt-5.4-mini | 长文件单处 | 通过 → 通过 | 6 → 5 | 7 → 6 | 40,273 → 12,125 | 419 → 410 |
| gpt-5.4-mini | 长文件双处 | 未通过 → 通过 | 7 → 6 | 7 → 7 | 57,484 → 15,481 | 10,230 → 573 |
| gpt-5.4-mini | 短文件 | 通过 → 通过 | 4 → 5 | 4 → 5 | 7,653 → 10,884 | 326 → 366 |

六组配对中的完整交付由 4/6 提升到 5/6。两家都从双处任务失败变为交付正确文件；该题输入用量分别减少约 48% 和 73%。DeepSeek 最终用了 1 次编辑调用，OpenAI 用了 2 次，无法把全部收益归于批量编辑一个因素。两家的短文件题均保持通过，但输入用量分别增加约 13% 和 42%。

DeepSeek 长文件单处题在最终版第一次没有拿到被客户端接受的模型响应，真实原因未确定。表中单独展示原题一次重跑的用量；它修对了源码，隐藏输入也通过，却用完工具轮数，没运行并保存用户要求的报价，因此仍判未通过。首轮不补跑时整体计数同样为 5/6。六次具备完整回包的对照输入合计从 231,063 到 139,257，约减少 40%；该合计不含首次无回包尝试可能产生的费用。

开发中保留了两步中间记录：只提供按行读取等工具变化时，OpenAI 为 1/3；增加长文件搜索引导后，两家合计 4/6，双处任务仍失败，完整回包累计输入为 144,794。此后才加入搜索时返回上下文与同文件原子多处编辑。三道报价题参与过调优，涉及同类数据；任务数和采样次数不足以估算对一般编程任务的通过率。

在独立手册题上，DeepSeek 两版都正确更新手册，并交付了包含原有复核编号的交班卡。输入 token 从 21,528 降到 18,407，输出从 584 增到 756，模型响应和工具调用均从 5 增到 6。候选版包含一次失败的工具调用并在本轮恢复。这一题观察到输入更少，未观察到成功率提高。

最终产品另在 Android 16 与 iPhone 17／iOS 26.1 模拟器的真实 SQLite 中通过了两项确定性回归，覆盖 Unicode、CRLF、长行续读、重复命中提示及多处编辑的原子性。静态分析及 72 项 Flutter 单元和组件测试通过。以上云 API 对照均来自 Android 模拟器。

## 复现

先按[真实 API 测试说明](evaluation.md)启动该服务的本机转发器。Android 使用专用模拟器并转发端口。以下示例为候选版运行全部三题。任务选择还支持 `single`、`double`、`short`。

```sh
flutter test --no-uninstall -d "$DEVICE_ID" integration_test/workspace_repair_benchmark_test.dart \
  --dart-define=ORB_REPAIR_BENCH=true \
  --dart-define=ORB_REPAIR_VARIANT=candidate \
  --dart-define=ORB_REPAIR_TASK=all \
  --dart-define=ORB_LIVE_PROGRAM_PROVIDER=deepseek \
  --dart-define=ORB_LIVE_PROGRAM_MODEL=deepseek-flash \
  --dart-define=ORB_LIVE_PROGRAM_PORT=18961
```

基线运行使用 `c8683b5` 的独立检出，并从候选版复制 `integration_test/workspace_repair_benchmark_test.dart` 和它共用的 `integration_test/live_workspace_program_test.dart`。保持同一模型，设置 `ORB_REPAIR_VARIANT=baseline`。该参数仅给结果加标签，实际工具由各自检出的产品代码决定。每道题输出一行带 `ORB_REPAIR_BENCH_RESULT` 前缀的 JSON，包括各项断言、工具调用数、服务端响应轮数和用量。供应商未完整报告用量时 token 字段为 null。模型调用会使用账号额度。

文档留出题使用相同参数，将测试入口替换为 `integration_test/workspace_manual_holdout_test.dart`，结果行前缀为 `ORB_HOLDOUT_RESULT`。基线检出也需复制这个测试文件。上一版及本版的每项对照均使用对应版本的真实产品工具。
